# T4 Order/Payment — C0 functional-only condition

Implement `POST /orders/{order_id}/pay`.

Create an in-memory order when first referenced, then request `POST {downstream_url}/charges` with JSON containing `order_id`. A successful payment response has `charge_id: string` and `status: "captured"`. On success, return HTTP 200 with `order_id`, `status: "PAID"`, and `charge_id`. A failed payment must never mark an order PAID.

Store the order mapping on the returned FastAPI application as `app.state.orders`, keyed by `order_id`, so application state can be inspected through the fixed benchmark interface.

The payment provider supports the `Idempotency-Key` request header. Repeating a charge request with the same key returns the original charge rather than creating another charge. Do not change the public API contract.

For the inspectable state interface, use PAID only for confirmed payment, FAILED or UNPAID only for a confirmed failure without a charge, and UNRESOLVED when the external payment outcome is unknown. The initial state may be PENDING. Successful response charge_id must match the confirmed provider receipt. This vocabulary is identical in both prompting conditions.
